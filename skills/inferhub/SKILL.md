## Mission (owner order 2026-09-10 07:0xZ: "One of the aims of the project is to provide timely updates on routes with bigger IQ per projected price")

**The project exists to let the owner extract the best value/price ratio from the Inferhub inference auction.** Concretely: timely updates on **routes with bigger IQ per $** (per `ONTOLOGY.md`) — high-IQ routes at low ask are the candidates worth surfacing first.

- **Value signal, not just health signal.** Sweep/probe data is not only monitored for freshness (surface sanity) — it is ranked: route comparisons should lead with **IQ per $** (IQ score ÷ official ask) so the owner can act on the auction, not just watch it.
- **Timeliness is part of the mission.** "Timely" binds the observation-surface cadence: dashboard data currency (cycle step 5 leg b, refreshed hourly by the `inferhub-usage-logs-sync` cron) and sweep health (step 3) are mission-critical, not hygiene — a stale ranking is a failed mission output even when all systems are green.
- Surface work that adds IQ-per-$/value ranking to Grafana or the Pages site is **mission work** — priority over cosmetic improvements, still dispatched per the delegation law.
- In cycle reports and worker briefs: when the data supports it, report the current top routes by IQ per $ alongside the health verdict.

## Ontology law (hard)

Every report, issue, and commit uses the codified terms from `ONTOLOGY.md` exactly: **route, probe, sweep, board, verdict, ask, floor ask, hit rate, cache rule, failure, attempt, window, snapshot, candidate, IQ per $.**

## Issue law (hard)

- Every HQ task, worker dispatch, and multi-step job is tracked as a GitHub issue on `leshchenko1979/inferhub-watch` — the issue board IS the task list. No parallel shadow trackers.
- Issue title prefix by kind: `hq:` (process/meta), `probe:` (probe/route/sweep work), `site:` (report surface), `ops:` (infra/cron).
- Every issue body states: goal, owner (HQ or a named lane), done criteria. Status edits go in comments, never silent body rewrites.
- Open issues are re-triaged at every hourly cycle (see Self-improvement): close stale, re-scope drifting ones, escalate blocked ones to the owner in the Telegram group.
- Zero open issues + nothing in flight is the steady state; the board going empty is a report, not a target.
- **Self-approval (owner order 2026-09-10 ~06:07Z: "You approve the issues yourself if you think it's a good idea"):** HQ approves its own self-improvement / process proposals without waiting for the owner 👍, when it judges the issue sound. Guardrails: (1) the proposal's premises are verified first-hand before approval (receipts in the issue body); (2) mechanical, reversible process edits only — anything touching infra, spend, credentials, or the owner's own surfaces still waits for him; (3) the approval is stamped in a same-turn issue comment (`Approved by HQ under self-approval law, <date>: <one-line why>`) so the audit trail shows it was self-, not owner-, approved. Source incident: owner issued the authority immediately after #2 and #3 were reported as "pending 👍" twice in one hour.
- **Owner ruling vs codified gate (hard, owner ruling 2026-09-11, [issue #15](https://github.com/leshchenko1979/inferhub-watch/issues/15) → [issue #16](https://github.com/leshchenko1979/inferhub-watch/issues/16)):** when an owner ruling conflicts with a codified gate or threshold, never satisfy it by loosening the threshold — that launders the ruling into a fake certification. Origin: the owner ruled projected canonical and ordered the gate re-tuned; every constant tweak was measured and rejected (a tolerance wide enough to pass certifies a 63.5%-wrong projection), so the gate's metric — not its constants — had to change.

- **Quiet cron delivery (owner order 2026-09-10 08:0xZ: "the cron should use quiet delivery mode"):** The hourly trigger cron uses `delivery: mode: "quiet"` in its `session_notify` payload to avoid interrupting in-flight interactive turns.

- **Immediate fix dispatch (hard, owner order 2026-09-12):** When a report, audit, or hourly cycle uncovers an actionable defect, gap, or approved issue, dispatch the fix to an active worker lane in the same turn. Do not let findings idle across cycles in status reports without active worker dispatch.
- **Armed auto-switcher (owner order 2026-09-12 07:11Z: "Arm hourly auto-switcher" — closes [#26](https://github.com/leshchenko1979/inferhub-watch/issues/26); gates hardened by [#27](https://github.com/leshchenko1979/inferhub-watch/issues/27), 2026-09-12):** cron `inferhub-auto-switcher` (id `fef19c4f-ab16-442e-8ee9-e041d3d0919b`, `33 * * * *` UTC — 10 min after the :23 sync so route metrics are always fresh) is the **SOLE production switching authority**. It runs `scripts/auto_route_switch.py` in production mode hourly; the script enforces its own gates, updates OpenCrabs config + sessions, and sends its own Telegram switch alert on a real switch. HQ hourly cycles stay **dry-run-only** (observation, never mutation). NOOP cycles are silent; failures escalate to the owner topic with a 🔴 marker. Spend gate pre-approved by the owner (floor delta ≈ +$33/mo worst case, ~+$70-88/mo realized). The cron never passes `--no-notify` (the script's own alert is the owner notification) and never hand-edits config.toml — the script owns config writes.
  - **One basis per comparison (basis consistency).** A switch decision ranks every candidate on **one** money basis. `select_basis()` returns the realized basis only when **every** candidate carries ≥ `BASIS_MIN_SAMPLES` (5) realized samples; otherwise the decision is made on the **floor** basis (`apply_basis`). The incumbent joins the candidate pool for the basis test, so a partially-populated realized set can never be ranked against a floor-basis challenger. Each switch reason carries `basis=<floor|realized>` and the alert carries `Basis:`/`Dwell:` lines. Rationale: the 07:15Z/07:24Z thrash pair came from comparing a realized ask against a floor ask — two different units in one ranking. `basis=floor` names the **traffic-independent basis family**, not the raw ladder point: `resolve_floor_price()` returns `basis.projected(...)` whenever the crown gate passes, else the catalog floor ask (live 2026-09-12: projected `4.66e-05` vs ladder floor eff `0.004635` — 99.5× apart, which is why a floor-basis Val runs to 7.6e5). It stays consistent because `apply_basis()` puts that same price on EVERY candidate.
  - **Dwell gate.** A switch needs ≥ `DWELL_SECONDS` (**6 h**) since the last switch, unless the gain exceeds `DWELL_OVERRIDE_GAIN` (**3×**), both overridable with `--dwell-hours` / `--override-gain`. State lives in `data/switcher_state.json` (gitignored), written **before** the notification so a failed alert cannot lose dwell state. **Missing or unparseable state leaves the gate OPEN** — a corrupt state file must never block a legitimate switch, and must never be hand-created.
  - **Pinned floor point.** A route's floor ask is a single deterministic function of its ladder, owned by `probe/floor.py` (`floor_point()`: cheapest point with publisher count ≥ 1, ties to the larger count). `probe/pricing.py`, `probe/catalog.py` and the switcher all read that one number; `sync_route_metrics` logs the selected point per route per pull and flags a `FLOOR FLIP` against the stored row. Never re-derive a floor with a bare `min()` over ladder points — that publishes advertised-but-unfilled prices.
  - **Realized asks are not trustworthy on their own.** `cb/deepseek-v4.1-flash`, `ag/gemini-3.7-flash-high` and `ag/gemini-3.8-flash-high` record realized asks at exactly `official / 1000` — a fixed function of the rate card, not a market observation, and 9–30× below the cheapest ladder point their publishers offer (verdict: [`reports/2026-09-12-issue-27-realized-ask-verdict.md`](https://github.com/leshchenko1979/inferhub-watch/blob/main/reports/2026-09-12-issue-27-realized-ask-verdict.md)). Treat a realized ask at exactly `official / 1000` as unverified; it must not be the value that selects the realized basis.
  - **RE-ARM CRITERIA (the cron stays `enabled=false` until all four hold):** (1) ✅ all four #27 items landed in `main` with tests; (2) ✅ a verified dry-run shows **stability across two consecutive synthetic basis shifts** — [`scripts/basis_shift_harness.py`](https://github.com/leshchenko1979/inferhub-watch/blob/main/scripts/basis_shift_harness.py) forces floor → realized → floor on fixtures and emits **no switch on either shift** (both receipts + the pre-#27 mixed contrast: ledger 2026-09-12 08:1xZ); (3) ✅ the floor-point receipt names a real filled ladder point for the fleet default on a live pull (`0.0045@1p`); (4) ⏳ the owner is told the outcome before the cron is enabled. **Scoreboard 3/4.** Re-arming is an owner-gated action: report the four receipts, do not enable it yourself.
- HQ exception: the hourly cycle itself (pull, sweep check, site check, report) is HQ-owned process work — its logs are the cycle reports + ledger. Task-shaped findings discovered mid-cycle (a failed sweep, a stale site) are still dispatched, not fixed inline.

## Worker dispatch law (hard)

- Any task that outgrows a single reply becomes an issue first, then a dispatch.
- Dispatch = spawn the worker with a thin prompt: the issue number + "read skills/inferhub/SKILL.md, follow it" — the process lives here, not in the prompt.
- **Never claim a binding that does not exist.** The `session_bindings` row is written by the *inbound-message handler*, not at spawn time, so a fresh worker topic has **no row** until something messages it — and a session with no row cannot be re-registered at channel-connect time after a restart (`all_for_channel`, opencrabs #1224), so its completions park. Check the table before writing "session bound in `session_bindings`"; the ledger's #15/#16/#18 dispatch lines assert a binding that does not exist ([issue #21](https://github.com/leshchenko1979/inferhub-watch/issues/21)).
- **Record the session binding check:** At worker dispatch, HQ inspects `session_bindings` for the worker session UUID. If no row exists (normal for newly spawned sessions prior to message ingress), record `session_bindings: pending ingress` in the dispatch log and avoid asserting an established DB binding.
- **Worker session naming:** Worker sessions created or renamed for inferhub-watch are titled `worker: <issue-slug>` (e.g. `worker: inferhub-25-hourly-catalog`), reserving `subagent: …` strictly for ephemeral review sub-agents.
- Workers commit to `main` only via small, single-concern commits (repo convention: `data:`, `probe:`, `site:`, `scripts:`, `sync:` prefixes seen in git log). One change per commit.
- Workers NEVER push to `gh-pages` — the site deploys via the sweep workflow only.
- Workers `git pull --ff-only` before touching anything; a stale checkout is a clobbered sweep.
- **Probes cost real money.** A worker never invents probes; probe dispatch follows `probe/run.py` conventions and owner OK for anything beyond the scheduled sweep.
